 1. PRODUCT OVERVIEW
================================================================================

1.1 One-liner
  "Listening tools tell you what was said. SIGNAL tells you what it means,
   how to say it back, and how sure we are - and installs it straight into
   your team's AI agents."

1.2 Problem
  When a marketer starts on a new topic, product or campaign, they need to
  know how real people talk and feel about it. Today that means manual
  scrolling (slow, biased), enterprise listening (expensive, keyword-bound),
  agencies (weeks), or generic AI answers (fluent but stale and
  unverifiable). Result: briefs built on assumptions, content that sounds
  like the brand instead of the audience, and AI content agents fed only
  with the brand's own copy.

1.3 Solution
  The user types a topic, product or campaign idea, e.g. "Gen Z and meal
  prep" or "launching a snack brand in the Netherlands". SIGNAL:
    1. Interprets the brief (topic, market, languages, audience, category,
       intent) and proposes a starting plan: hypotheses, research
       questions, starting sources with reasons.
    2. Runs an AGENT LOOP that collects discourse tool call by tool call:
       it tries a source, sees how relevant the results are, drops weak
       sources, digs into strong ones, and fills gaps in the research
       questions - explaining every move. Hard limits keep cost and time
       bounded.
    3. Cleans everything inside the tools: privacy (hashed authors,
       redaction), date window, de-duplication, spam, relevance.
    4. Extracts needs, pains, objections, emotions and phrases; clusters
       them; computes counts and strength in code.
    5. Writes a grounded Context Pack where every claim cites verified
       evidence, then checks every quote and claim.
    6. Delivers the pack as a web page for people, JSON/MCP for agents,
       and an installable skill so a team's agents use the audience's
       voice automatically.

1.4 Product principles
  P1  Evidence or it didn't happen. Every claim cites real evidence;
      inferences are labelled as inferences.
  P2  The audience's words over ours. Lead with verbatim language.
  P3  Show your working. Every source decision has a visible reason.
  P4  Confidence is a first-class field, never hidden, never colour-only.
  P5  Actionable by default. Every section ends in something to copy,
      export or hand off.
  P6  One engine, two interfaces. JSON contract first; the human page is a
      rendering of the same data with the same IDs.
  P7  Respect people and platforms. Privacy and compliance are features.
  P8  Simple beats clever. Fewer moving parts, more time on insight.

 2. GOALS, NON-GOALS, AND JUDGING CRITERIA
================================================================================

2.1 Goals
  G1  A marketer gets a usable, evidence-backed pack in <= 12 minutes.
  G2  An AI agent can request, read and act on a pack via MCP or REST, or
      by installing the exported skill, without custom integration.
  G3  Zero fabricated quotes reach the user.
  G4  The agent's source choices are visible and explained.
  G5  Specific enough that a marketer would use it today.

2.2 Non-goals
  Always-on monitoring or alerts; archives beyond 12 months; profiling of
  individuals; private content (private groups, DMs, closed profiles,
  membership-approved content); mobile apps, billing, team
  workspaces; Word/PowerPoint export.

2.3 How the product meets the judging criteria

  TECHNICAL IMPLEMENTATION
    - Agent loop chooses sources per brief, adapts to results, fills gaps,
      and states a reason for every call (Section 8)
    - Code-owned data handling inside every tool: normalisation, hashed
      authors, redaction, date window, de-duplication, spam, relevance
    - Staged LLM processing; schema-validated outputs with retry
    - Verification: exact-substring quotes + entailment check; strength
      computed from verified clusters
    - Public, modular, reproducible code; run log and cost per run

  CREATIVITY (what "context" means)
    - Seven layers + meta; claim model (observed / inferred / external,
      confidence with counts, safe_to_assert)
    - Platform lens, emotion mix, white space, tensions, segments,
      moments, generic-AI-vs-found comparison
    - Delivered as an installable skill - context that lives inside the
      team's agents, not in a PDF

  USABILITY
    - One input box; plan with reasons; live Theatre showing each agent
      move; brief-first pack page; receipts in one click
    - Agent UX: stable IDs, lowercase enums, digest + full views,
      guardrails, instructions_for_agents, MCP, skill export, SCHEMA.md

  IMPACT
    - Do this first (3 actions), channel plan, hooks, creative brief,
      this-week plan, objection handling, say / don't say, compliance
      flags
    - Prompt block and skill in two clicks; Markdown and PDF for teams

================================================================================
 5. WHAT "CONTEXT" MEANS (THE CREATIVE BET)
================================================================================

Definition:
  "Everything a smart person who just spent two weeks immersed in this
   audience's conversations would know - and that a newcomer, human or
   agent, would need to act credibly - packaged so it can be checked and
   reused."

5.1 Seven layers + meta

 Layer                      Question                    Contents
 -------------------------  --------------------------  ------------------------
 1 LANDSCAPE                What's the shape of the     Themes with size, emotion
                            conversation?               mix, momentum or new-in-
                                                        30-days; PLATFORM LENS
 2 LANGUAGE                 How do they talk?           Lexicon, phrases, slang,
                                                        code-switching, tone,
                                                        say this / not this
 3 TENSIONS & MOTIVATIONS   Why do they care?           Needs, pains, jobs,
                                                        "want X but Y" tensions,
                                                        segments, emotions
 4 BELIEFS & OBJECTIONS     What do they doubt?         Objections, myths, trust
                                                        markers, competitors
 5 CULTURE & CODES          What's the vibe?            Formats that perform,
                                                        communities, public
                                                        creators, codes
 6 MOMENTS                  When does it matter?        Rituals, seasons,
                                                        holidays, paydays
 7 IMPLICATIONS             So what do we do?           Do this first, channel
                                                        plan, WHITE SPACE,
                                                        opportunities, hooks,
                                                        creative brief, this
                                                        week, compliance, risks
 META                       How sure, and how found?    Agent decision log,
                                                        sources used/dropped,
                                                        coverage, blind spots

5.2 Signature insights
  - TENSIONS: opposing needs held at once - where creative angles come from
  - SEGMENTS: the audience is 2-4 groups, not one
  - PLATFORM LENS: the same topic framed differently per platform
  - WHITE SPACE: needs voiced repeatedly that nobody serves, and questions
    in threads that got no useful reply
  - GENERIC VS. FOUND: what a generic AI answer would say (generated once,
    no evidence) next to what the evidence actually shows
  - VOICE FINGERPRINT: tone, humour, slang, emoji, code-switching
  - GROUNDING: every claim traceable to verified evidence

5.3 Claim model (every insight item)
  claim            One sentence a person could say out loud
  cluster_id       The verified cluster the claim summarises
  evidence_ids     Receipts: a sample of the cluster's evidence (max ~5)
  strength         evidence_count, distinct_authors, platforms,
                   engagement_percentile_median - computed in CODE from the
                   cluster's verified members
  counts           {matching, of_total}: verified cluster members / relevant
                   posts in the pack; shown as "12 of 248 posts"
  confidence       {score 0-1, label strong | moderate | emerging |
                   speculative}
  claim_type       observed | inferred | external
  safe_to_assert   true ONLY if strong AND observed AND verified
  non_obvious      true if not covered by the generic AI answer
  emotion          list from the emotion enum (where relevant)
  trend            rising | stable | fading | insufficient_data
  recency          median date of dated evidence
  segment_ids, related_ids

5.4 Confidence: definitions, score and labels  (defaults: config/scoring.yaml)
  Definitions
    platform   the source family: reddit, tiktok, youtube, instagram,
               web_forum, web_review, web_editorial. All forum domains
               together are ONE platform (web_forum); distinct domains
               count as distinct SOURCES.
    source     a distinct source unit (subreddit, hashtag, channel,
               query) or a distinct web domain
    author     a distinct author_hash; a web page with no detectable
               authors counts as one author
    members    verified cluster members, excluding short_form posts
  Score (each component 0-1; computed in code, never by a model)
    volume         = min(1, members / 12)
    authors        = min(1, distinct_authors / 8)
    cross_platform = min(1, (platforms - 1) / 2)   1 -> 0, 2 -> 0.5, 3+ -> 1
    engagement     = engagement_percentile_median / 100
    recency        = share of dated members in the newer half of the time
                     window; 0.5 if no member is dated
    verifier       = 1 if supported, 0.5 if partially supported
    score = 0.30 volume + 0.25 authors + 0.20 cross_platform
          + 0.10 engagement + 0.10 recency + 0.05 verifier
  Labels: the highest level whose score threshold AND gates all pass
    strong       score >= 0.75; >= 8 members; >= 5 authors; >= 2
                 platforms; claim verified as supported
    moderate     score >= 0.50; >= 4 members; >= 2 sources
    emerging     score >= 0.30
    speculative  everything else, and all unverified inferences
  Caps: one author supplies > 50% of members -> at most emerging;
  thin-evidence run -> at most emerging; "partially supported" -> one
  level down and claim_type inferred.
  Worked examples (also unit tests): 12 members, 8 authors, 3 platforms,
  engagement 60, recency 0.6, supported -> 0.92 strong. 10 members, 6
  authors, 2 platforms, rest the same -> 0.71 moderate.
  Gates are necessary, not sufficient. Weights may be recalibrated once on
  Day 3 against the flagship packs; any change goes into scoring.yaml and
  the decision log and is shown in the pack's Method section. Stored
  labels are lowercase; the UI capitalises them.

5.5 Opportunity score  (defaults: config/scoring.yaml)
  Computed in code per opportunity from the need or white-space cluster it
  builds on. All components are 0-1 and shown next to the score.
    demand          = min(1, members / P90 of member counts in this pack)
    dissatisfaction = share of members with a pain, a negative stance,
                      frustration, or an unanswered question
    novelty         = 1.0 if non_obvious, else 0.4
    saturation      = share of members naming a brand or product as
                      solving the need (brand mention + positive stance)
    score = demand x dissatisfaction x novelty x (1 - saturation)


================================================================================
 6. THE CONTEXT PACK SPECIFICATION
================================================================================

6.1 Deliverables (one underlying object)
  context_pack.json  Canonical, versioned (schema_version "1.0")
  Pack page (web)    Human view with drill-down to evidence; shareable link
  Skill (.zip)       <slug>/SKILL.md + references/ - installable in Claude
                     and other skills-compatible agents (6.7)
  Prompt block       <= 1,800 tokens to paste into any AI tool
  Markdown           brief.md - "Copy for Notion / Docs"
  Print / PDF        Print stylesheet: the pack page prints as a clean
                     brief (browser "Save as PDF") for decks and sharing
  Excel workbook     [P1] <pack>.xlsx - one tab per main section,
                     clickable links, same IDs, formula-safe cells
  Digest             <= 500-token view for agents
  MCP + REST         Programmatic access

6.1b Condensed content (change V4, schema 1.1)
  Every section has one job, and every insight appears ONCE, in the
  section whose job fits it best; elsewhere it is a link, never a
  restated paragraph.
    Themes          what people talk about and how they frame it
    Pain points     what gets in their way (pain_points[], PAIN-xx; the
                    pains that used to sit among motivations)
    Tensions        where people feel torn (two sides, both shown)
    Objections      why they would say no to a product like this, with a
                    counter-angle (inferred; tailored to intake.offer, or
                    "adapt to your offer")
    Motivations     what they want to achieve (needs and jobs)
    Landscape       how the conversation differs by place and over time
                    (platform lens; "what's new" folded in) - never a
                    re-statement of themes
    What performs   leads with 1-3 takeaways (a concrete recommendation
                    and why); the example posts sit underneath
  After writing, a consolidation step (code similarity of the claims and
  their evidence first, then one small model call only for borderline
  pairs) finds items in different sections that state the same finding:
  the one in the best-fitting section stays, absorbs the other's
  evidence, and the other section links to it (sections_meta.see_also).
  Items link to connected items in other sections from shared evidence
  (relations[]: comes_from, blocks, related - e.g. an objection shows the
  pain behind it and the motivation it blocks as small chips). Every
  section opens with a one-line so_what tied to brief.intake.goal (or the
  intent). Hypotheses move to Method (a table: supported / refuted /
  inconclusive); moments become timing on channel cards (V7). An empty
  section never appears blank: sections_meta gives empty_reason in plain
  words and 1-2 next steps. Item counts stay the same or go down.

6.1c Opportunities you can trust (change V5, schema 1.1)
  "White space" is called Opportunities everywhere the user reads it.
  One opportunities[] list replaces white_space[] and the scored
  opportunities: {id OPP-xx, opportunity, kind (content_idea |
  product_idea | positioning), evidence_ids, distinct_authors,
  communities, existing_solutions[] {name, url}, search_note, status,
  confidence, builds_on, related_ids, score (PRD 5.5, when computed)}.
  - status "supported" only with at least N distinct authors across at
    least 2 communities (scoring.yaml opportunities); otherwise "signal",
    confidence at most emerging, shown as "early signal - check before
    acting". A single post is never supported. Counts are code.
  - Before anything is called unserved, one web search per opportunity
    (modes.yaml opportunities.searches_max) for existing products,
    services or content in the brief's markets. Found: existing_solutions
    lists them (only URLs the search returned) and the opportunity is
    reworded as a gap in HOW it is served (price, fit, language, format).
    Not found: search_note "no existing solution found in our search".
    Never "nobody serves this" (checked in code).
  - Migration: old white space and scored opportunities become
    opportunities with status "signal"; their ids are renamed everywhere.

6.1d News hooks and timing (change V7, schema 1.1)
  - news_hooks[] (at most 5): {id NWS-xx, headline (own words), date,
    kind (news | regulation | event), source_url, why_it_matters,
    related_ids, claim_type external}. One web search step after
    collection, in the brief's languages, for the last 30 and next 90
    days (modes.yaml news), tied to the top themes and pain points.
    Kept only when the URL came back from the search and the date is in
    that span: no URL -> dropped; never from model memory.
  - channel_plan[].timing[]: {label, when, why, evidence_ids, claim_type
    observed | external, source_url, item_id}. Observed: the pack's
    moments, and weekdays / seasons / times of day named in at least 2
    posts on that channel's platform (code). External: upcoming news
    hooks and calendar facts (budget cycles, deadlines) ONLY with a cited
    URL. A chip without its receipt is refused by the schema.
  - playbook.this_week[].news_hook_id may link a hook. UI: "Ride this
    now" in the summary; chips on channel cards; "Rides the news" in
    the this-week plan.

6.1e Post briefs, drafts and a content calendar (change V8, schema 1.1)
  - post_briefs[] (modes.yaml posts.briefs_min-briefs_max, 5-8), written
    in the playbook call from pain points, objections, hooks,
    opportunities and news hooks: {id PST-xx, channel (the user's
    channels_in_use first, else the channel plan), role, goal, hook,
    hook_id, angle, key_points[3-5] {text, item_ids, evidence_ids},
    structure ("story -> lesson -> question"), format (text_post |
    carousel | short_video | blog_article | newsletter),
    their_words_to_use[] (LEX ids), cta, avoid[] (exact guardrail
    phrases from not_this / never_claim), news_hook_id, based_on[],
    confidence}. Code keeps a key point only when its items exist; its
    evidence_ids come from those items (never from the model); a brief
    with fewer than 3 key points, or on a channel with no evidence, is
    dropped. Confidence = the weakest label among the items it uses.
  - drafts[] (posts.drafts, 3): full posts for the first briefs, in the
    brand voice if given, else neutral-professional, sized per format
    (posts.draft_chars). ONE extra call in the playbook stage (brand
    voice is still used nowhere else). Code removes any sentence that
    uses a not_this / never_claim phrase, and any sentence with a
    number, percentage or price that does not appear in the brief's
    cited evidence; removed_sentences counts them. Every draft carries
    the label "Draft - review before posting" and goes through the
    compliance review with the hooks.
  - content_calendar[] (posts.calendar_weeks, 4): {id CAL-xx, week,
    suggested_day, channel, post_brief_id, timing_reason, timing_kind
    (news_hook | channel_timing | spread), status "idea"}. Built in
    code: a brief that rides a dated news hook goes in that week; days
    come from the channel's timing chips that name a weekday, else from
    this week's plan; never more posts per week on a channel than its
    posts_per_week in the channel plan.
  - Exports: the calendar as a Notion-importable CSV (Title, Week, Day,
    Channel, Audience, Hook, Angle, Key points, Call to action, Status,
    Pack link, Source links; UTF-8 with BOM; formula-safe cells, DH11)
    and as a table in brief.md ("Copy for Notion"); briefs and drafts in
    brief.md, the prompt block and the skill (references/posts.md). API:
    GET /packs/{id}/post-briefs, /packs/{id}/calendar, export kind
    "calendar"; MCP: get_post_briefs(pack_id), get_calendar(pack_id).

6.1f Pack page and hand-off (change V9, schema 1.1; revised after a
     marketing-director audit, docs/04_Changes_Plan.md)
  - Page in three parts plus the research: SUMMARY (fits one laptop
    screen: who it is for, snapshot.represents, snapshot.findings - the
    top 3 with one quote, its English translation, plain strength words
    "N people, M communities" and "good enough to" from scoring.yaml
    plain_labels -, snapshot.position, the plan's first 3 moves with
    their success_measure, up to 2 news hooks); UNDERSTAND YOUR AUDIENCE
    (their words; what they want / what stops them with tensions as the
    bridge; segments; generic answer vs. the posts with a status per
    generic point - confirmed | contradicted | not_seen - from the
    non-obvious check, no new call; landscape); ACT ON IT (one plan:
    post briefs + 4-week calendar, this week = week 1; channels; what
    performs; opportunities; guardrails, with the rest of the playbook
    folded away); THE RESEARCH (collapsed).
  - Trust: a thin-evidence pack shows the coverage grade at most
    scoring.yaml grade_cap_thin (c) with snapshot.grade_note, and no
    finding in it is "good enough to commit budget". Every strength
    badge has its plain words as a tooltip; "How to read this" lists
    them (GET /reading-guide).
  - position and success_measure (do_first, post briefs) come from the
    playbook call (no new call). Packs made before V9 get findings,
    represents and the grade cap in code when read; position and the
    comparison stay empty.
  - Hand-off (GET /packs/{id}/handoff): Quick brief (new, at most
    exports.quick_brief_max_words), Brief for your AI writer, Full
    report, Content calendar, Print / Save as PDF (Summary = page 1);
    under "More": Teach Claude (skill) and For developers (JSON, API).
    Each shows purpose, length in pages (exports.words_per_page) and a
    one-line preview; a toast says what was copied. "Send to Notion" is
    not built (no new service). Replay is called "Watch how this pack
    was made". brief.md and print follow the page order.

6.1g Ask this pack (change V10)
  - POST /api/v1/packs/{id}/ask {question, history[]}: a READ-ONLY tool
    loop (reasoner role) over get_pack_view, get_insight and
    search_evidence for that one pack; limits in modes.yaml ask
    (max_tool_calls reads, max_usd per answer, history_max turns).
    Posts reach the model only inside <untrusted_user_content> tags.
  - The answer cites [ID]s; code keeps only ids that exist in the pack
    (others are stripped) and turns them into numbered citations that
    open the source post (a finding opens its first post). No evidence
    -> the answer says so plainly; no outside facts (prompts/ask.md).
  - Cost: every call counts against DAILY_SPEND_CAP_USD; without a run
    key each pack takes ask.questions_per_pack_per_day questions per UTC
    day (table ask_counts), then a friendly message. Costs are never
    returned.
  - Pack page: "Ask this pack" side panel with 4 suggested questions
    built from the pack in code. MCP: ask_pack(pack_id, question), run
    key required. LLM_FAKE answers come from a fake in agent/ask.py.

6.3 Common item shape
  {
    "id": "TEN-02",
    "type": "tension",
    "claim": "Students want to eat healthy but refuse to give up Sunday.",
    "summary_for_humans": "...",
    "cluster_id": "CL-07",
    "counts": {"matching": 41, "of_total": 248},
    "confidence": {"score": 0.78, "label": "strong"},
    "claim_type": "observed",
    "safe_to_assert": true,
    "non_obvious": true,
    "strength": {"evidence_count": 41, "distinct_authors": 37,
                 "platforms": ["reddit","tiktok","youtube"],

================================================================================
 8. THE AGENTIC COLLECTOR
================================================================================

8.1 Principle
  The agent decides WHERE to look; code owns the DATA and the LIMITS.

8.2 Loop
  A plain tool-use loop on the Messages API (no Agent SDK): send messages
  -> run requested tools -> append results -> repeat, until finish() or a
  limit. Model: Sonnet. Input: the brief interpretation, the starting
  plan, the research questions, the budget.

8.3 Tools (every tool requires a "reason" argument and its description
    states its typical latency, measured on Day 1)
  search_reddit(target, limit, reason)        subreddit or search query
  search_tiktok(target, limit, reason)        hashtag or query; comments
                                              collected for top videos
  search_youtube(query, limit, reason)        videos + comments
  search_instagram(hashtag, limit, reason)    only if the actor verifies
                                              (cut list item 1)
  web_search(query, country, language, reason) returns candidate forum,
                                              review or article URLs
  fetch_and_segment(urls, reason)             reads pages, keeps posts that
                                              are exact substrings
  get_trends(terms, geo, reason)              Google Trends (external)
  coverage_report()                           evidence per research
                                              question and per source unit;
                                              budget, calls and time left
  finish(summary, source_verdicts, gaps)      ends collection

  Typical latency (defaults; Day 1 measurements in config/catalog.yaml
  replace them): web_search ~10-20 s; fetch_and_segment ~20-60 s;
  search_reddit ~30-90 s; search_youtube and search_tiktok (with chained
  comments) ~60-180 s; get_trends ~30-60 s; coverage_report instant.
  Parallel calls from one model turn run concurrently (max 3), so the
  agent batches independent calls into one turn.

8.4 What a tool does inside (before the agent sees anything)
  run actor / search / fetch -> normalise -> hash authors (raw names
  discarded in the same function) -> redact PII -> [24 h cache of these
  cleaned items] -> normalise dates and
  apply the window -> de-duplicate against the store -> spam filter ->
  relevance + language (Haiku batch) -> store. Then return ONLY: status,
  source_unit, collected / kept / relevant counts, relevant share, top new
  terms, 2-3 short samples wrapped as untrusted content, budget left.

8.5 Limits (enforced in code, never only in the prompt; values live in
    config/modes.yaml - this table mirrors it, and config wins)
                    Quick        Standard
  Tool calls        15           30
  Collection time   5 min        10 min
  Apify budget      1.80 USD     4.00 USD
  LLM budget        1.40 USD     3.50 USD (collection: plan, agent loop,
                                             tools)
  Analysis LLM      1.00 USD     2.50 USD (after collection: extraction,
  budget                                     clustering, writing,
                                             verifying, playbook)
  Item budget       600 raw items  2,000 raw items
  Per source unit   <= 30% of the item budget
  Minimum to finish >= 60 relevant docs (quick), >= 200 (standard), or
                    budget/time exhausted
  - Tools refuse to run when the budget, call or time limit is reached.
  - The two LLM budgets are separate, so an expensive collection never
    starves the pack. Each run stores its total LLM spend and, separately,
    the part spent on analysis (runs.cost_analysis_llm_usd).
  - finish() is refused unless coverage_report() was called after the last
    collection call; source_verdicts must name every source unit used.
  - The agent can only call the allowlisted tools; no general HTTP, file
    or shell access.
  - With concurrency and typical latencies, a Quick run fits roughly 6-10
    collection calls in 5 minutes; the call cap is a ceiling, not a
    target.

8.6 Fallback and top-up
  Crash: on loop error or timeout without finish(), code runs the
  starting plan's units NOT yet tried, in order, with default limits, and
  logs "fallback used".
  Low evidence: if finish() arrives (or a limit is hit) with fewer than
  min_relevant docs, code TOPS UP from units the agent marked kept: the
  next page of results, more comments, or follow-up queries the agent
  proposed in those communities, until min_relevant, the budget or the
  time cap is reached. Logged as "top-up used".
  Never: re-running a unit the agent dropped, or repeating an identical
  call (it would only return cached duplicates).
  If evidence is still short, the pack is a clear thin-evidence pack
  (6.6). The user always gets a pack.

8.7 What the system prompt says (and does not say)
  Says: reason from the brief's market, language and audience; try local-
  language queries first for non-English markets; look for local forums
  and review sites via web search; keep expat and local voices separate;
  prefer first-person discussion over brand content; batch independent
  calls in one turn and plan around each tool's latency; keep any one
  source unit under 30% of the item budget; check coverage regularly;
  drop sources with low relevance and say why; fill research questions
  with little evidence; stop when questions are answered.
  Never contains per-brief or per-market source lists.

8.8 Visibility
  Every tool call -> a decision_log entry and a Theatre event: source unit,
  reason, result summary. finish() verdicts become sources_used /
  sources_dropped with reasons.


================================================================================
 9. DATA HANDLING, PRIVACY, AND COMPLIANCE
================================================================================

 DH1  Public content (X posts and replies included), plus content
      visible to ANY logged-in user (change V6: LinkedIn posts and
      comments); never private groups, DMs, closed
      profiles or membership-approved content. Maintained Apify actors
      that need no session of ours (no cookies); no circumvention.
      Evidence from such sources carries requires_login = true.
 DH2  Collection cache by (tool, target, language, date) for 24 h on the
      container disk (temporary; fine to lose). The cache stores items
      AFTER author hashing and redaction - never raw actor output.
 DH3  Author handles hashed with a secret salt at ingestion, web-page
      authors included; raw names are never stored, logged, cached,
      emitted or passed to a later prompt by SIGNAL. Raw run data held
      by the scraping provider (Apify) expires under that provider's
      standard retention; the Method page says so (10.2 S3).
 DH4  Redaction of emails, phone numbers, @handles, profile URLs;
      evidence.redacted = true when text changed.
 DH5  Quotes in packs <= 280 characters.
 DH6  Retention: documents deleted after 30 days (configurable); packs
      keep redacted excerpts only.
 DH7  Dates normalised (incl. relative dates in en / nl / de); posts
      outside the window dropped; undated posts kept as evidence but
      excluded from trends and recency.
 DH8  Creator targets: public accounts only, by topical relevance.
      LinkedIn is searched by keyword only - never by person or profile,
      never to build a profile of an individual. The same holds for X
      (keywords or a #hashtag; never an @handle, profile or list).
 DH9  Prompt-injection defence: scraped text only inside
      <untrusted_user_content> tags; trust field on evidence; agents told
      never to follow instructions in evidence; collector has no
      dangerous tools.
 DH10 Every insight traceable to evidence with URL and date.
 DH11 Spreadsheet cells from scraped text are formula-safe (P1 Excel).
 DH12 Quote links survive redaction: text_fragment_url uses anchor words
      from the ORIGINAL text, chosen to contain no PII; quotes prefer
      spans without redactions; if a quote must include one, the drawer
      says "redacted - the live post shows the original wording". Links
      are tested on real Dutch and German pages on Day 1. Quotes in the
      summary and key findings prefer posts anyone can open
      (requires_login = false) when an equally strong quote exists;
      otherwise the drawer says "you may need to log in to LinkedIn to
      view this".

13.1 Deployment and job model
  - ONE Render Free web service serves the web app, /api/v1, SSE and
    /mcp. Free-instance limits shape the design: 512 MB RAM, a fraction
    of a CPU, a temporary disk, possible restarts at any time, 750
    instance hours a month, and sleep after 15 minutes without inbound
    requests (an open SSE stream does not count).
  - Keep-alive: GitHub Actions calls /ping every 10 minutes (24/7 uses
    about 744 of the 750 hours, so this is the only free web service).
    /ping never touches the database, so Neon still scales to zero and
    stays within its free compute hours.
  - Job model: approval puts a run in the runs table as "queued"; a worker
    loop in the same process claims one run at a time with a row lock and
    a heartbeat. Every stage saves its output to Neon and writes its
    events to the events table; SSE streams from that table. A run whose
    heartbeat stops is resumed once from its saved corpus (or packaged
    from what was stored).
  - Memory: one uvicorn worker, documents streamed to Neon, stages load
    only what they need, peak memory logged per stage (NFR9). Day 2 test:
    a Standard run below 400 MB.
  - Fallback: if the Day 2 memory test fails, the same worker code runs
    on Modal (free credits, no card); Render keeps every public endpoint.
  - Insurance: a static mirror of the featured packs on GitHub Pages.
  - Deploys: every push to main redeploys; push at most twice a day and
    never during judging.

 19. GLOSSARY
================================================================================
  Context Pack     The structured output: seven layers + meta, JSON-first
  Agent loop       Claude calling collection tools step by step until done
  Tool             A Python function the agent can call; it does the data work
  Source unit      A platform plus a specific community, hashtag, channel,
                   domain or query
  Fallback plan    Untried starting-plan units, run by code if the loop
                   crashes
  Top-up           More collection from kept units when evidence is short
  short_form       A post under 4 words: lexicon only, never counted
  Claim            One statement in the pack, backed by evidence
  Cluster          A verified group of posts behind one claim (CL-xx)
  Evidence         A verbatim, redacted excerpt from a public source
  Tension          A contradiction the audience lives with ("want X but Y")
  Platform lens    How the same topic is discussed differently per platform
  White space      Needs or questions nobody is serving or answering
  Observed / Inferred / External   Said by people / our synthesis / from
                   search, trends or editorial data
  safe_to_assert   Flag telling agents a claim can be stated as fact
  Skill            A folder with SKILL.md + reference files that AI agents
                   load when relevant
  Actor            A ready-made scraper on Apify
  MCP              Model Context Protocol: how AI agents call tools
  SSE              Server-Sent Events: live updates to the browser
