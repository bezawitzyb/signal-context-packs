V1. NEVER LOSE A RUN: RELIABILITY AND PERSISTENCE        (value rank 1)
--------------------------------------------------------------------------
1. Investigate first: find why a run whose agent loop failed showed
   "stopped early, the pack uses what was collected" but never produced
   a pack. Explain the root cause to me in plain English before fixing.
2. Guarantee: any run with >= the minimum relevant docs (scoring.yaml)
   ALWAYS ends with a pack, whatever fails after collection (agent loop
   error, timeout, a failed synthesis call). The pack is marked partial
   and the failure is stated in blind_spots and Method.
3. Below the minimum, the run ends on a clear thin-evidence screen that
   says why in plain words (e.g. "this audience seems to read more than
   it posts", "very few posts in the chosen languages") and offers
   one-click re-plans: broaden audience, include English, widen the time
   window, run Standard. Never a silent hang.
4. Persistence: runs and packs are saved in Neon (PRD FR-H7). If packs
   only live in browser memory today, fix that. Every pack has a
   permanent link /packs/{id}; every run has /runs/{id}. Refreshing or
   reopening the progress page reconnects to the same run from its last
   event - it never restarts or pays twice.
5. Inputs are never lost: the form keeps its values after a failure or
   refresh; every pack and failed run has "Run again with these inputs",
   which opens the form fully pre-filled (brief, clarifying answers,
   brand voice, mode).
6. Home page "My packs": packs created in this browser (ids in
   localStorage, wrapped in try/catch) plus featured packs.
7. Remove the "not persistent" warning once this works.
CHECK: raise an exception mid-loop, mid-synthesis and on timeout (tests)
-> a partial pack or the thin screen each time; refresh the progress
page mid-run -> it continues; reopen a pack link -> it loads; "Run

V3. SMART CLARIFYING QUESTIONS                            (value rank 2)
--------------------------------------------------------------------------
  [Superseded in part by V11 (docs/05_Brief_Understanding_Plan.md, PRD FR-A2d): goals and offer are
  always asked when missing and cannot be skipped; max_questions is 4; agents must pass goals.]
Replaces PRD FR-A2's "at most one clarifying question" and decision D2.
The goal: before planning, the agent asks the few questions that will
most improve THIS research, based on what the user already typed - not a
fixed form.

1. After the user types a brief (and optional brand voice) and clicks
   Plan, one interpretation call reads the brief and produces:
   - the interpretation (topic, markets, languages, audience,
     competitors - as today, with "assumed" flags), and
   - clarifying_questions[] (0 to max in modes.yaml, default 3):
     {id, question, why_it_helps (one short line shown to the user),
      fills (audience_roles | goal | offer | channels_in_use | market |
      competitors | timeframe | other), options[] (3-5 answer chips
      written for THIS brief), multi_select, allow_free_text}.
2. How the agent chooses questions (put this in the interpreter prompt
   and the PRD):
   - Find the gaps that would most change sources, research questions
     or the usefulness of the output, and ask about those first. Typical
     high-impact gaps: who exactly the user wants to reach (e.g. B2B
     buyer vs. influencer vs. end user; consumer vs. retailer), what the
     research is for (content calendar, campaign, positioning, product
     research, sales), what they offer, which market, which channels
     they already use.
   - Never ask about something the brief already answers; never ask
     generic questions that would fit any brief.
   - Phrase questions in the user's terms and the brief's language, with
     answer chips specific to the brief. Example for "digital
     manufacturing software, Europe": "Who should this speak to?" ->
     "Plant managers who sign off budgets" / "Operations and CI leads
     who champion tools" / "Operators on the shop floor" / "All of
     them".
   - If the brief is specific enough, ask nothing and go straight to the
     plan.
3. UI: questions appear as cards with tappable chips, a free-text
   option, and "Skip - let the agent decide" per question plus "Skip all
   and plan". Answers are shown back as editable chips on the
   interpretation screen (markets, languages, audience, roles,
   competitors - competitors labelled "Starter list - edit or add
   yours"); any edit re-plans in place without retyping. User-added
   competitors are always searched.
4. Answers are stored in brief.intake: {audience_roles[], goal, offer,
   channels_in_use[], competitors_user[], timeframe, other_answers[]}
   plus the questions asked. Research questions and hypotheses are
   generated per selected role; evidence carries role (buyer |
   influencer | user | consumer | other | unknown) when a post shows it.
5. Brand voice keeps its field with helper text
6. Agents (API/MCP) are never asked: they may pass the intake fields,
   otherwise defaults apply ("agent decides").
7. Eval: add to the harness - a specific brief gets 0-1 questions; the
   vague "snacks" brief gets questions about market and audience; the
   manufacturing brief gets a buyer/influencer/user question; no brief
   gets a question its text already answers.
CHECK: questions differ per brief and fit it; answering changes the
research questions and plan; "Skip all" still works; an over-specific
brief goes straight to the plan; "Run again" (V1) restores answers.

V4. CONDENSED CONTENT: EVERY INSIGHT ONCE, IN ITS BEST PLACE
                                                          (value rank 4)
--------------------------------------------------------------------------
Keep the sections that answer different questions (tensions,
motivations, objections, pain points, themes and so on) - do NOT replace
them. Fix the repetition: today the same finding shows up in several
sections in slightly different words. Each insight must appear once, in
the place where it is most useful, and be linked from anywhere else it
is relevant.

1. Give every section one clear job (write these in the PRD and in the
   section-writer prompt), e.g.:
   - Themes: what people talk about and how they frame it
   - Pain points / needs: what gets in their way
   - Tensions: where people disagree or feel torn (two sides, both shown) 
& Objections: why they would say no to a product like this, with a
     counter-angle (inferred; tailored to brief.intake.offer if given,
     else "adapt to your offer")
   - Motivations: what they want to achieve
   - Landscape / platform lens: how the conversation differs by place
     and over time - not a re-statement of themes
   - What performs: what kind of content works and why
2. Canonical home + links: after synthesis, a consolidation step (code
   similarity check first, then one small model call only for the
   borderline pairs) finds items across sections that express the same
   finding. It keeps the item in the section whose job fits best,
   merges the evidence into it, and replaces the duplicates with a link.
   Schema: every item gains related_ids[] (links to connected items in
   other sections, e.g. an objection linked to the pain point behind it
   and the motivation it blocks) and items keep one primary location.
3. Show connections instead of repeating: on an objection card, the
   pain point behind it and the motivation it blocks appear as small
   linked chips ("comes from: legacy machines are hard to connect"),
   not restated paragraphs. Same pattern everywhere.
4. Every section opens with a one-line so_what tied to the user's goal
   (brief.intake.goal): what this section means for them.
5. What performs leads with a takeaway (a concrete recommendation, e.g.
   "Ask a specific shop-floor question rather than a vendor question")
   and why; example posts are collapsed underneath.
6. Merge the old small sections: moments -> timing inside channel cards
   (V7 fills it); hypotheses -> a table in Method with status supported
   / refuted / inconclusive; whats_new -> folded into Landscape.
7. Empty sections never appear blank: show empty_reason in plain words
   and 1-2 next steps (e.g. "Too few people described themselves to form
   segments - try adding a role or running Standard").
8. Keep or lower item counts; use the freed budget for sharper writing.
CHECK: on a fixture pack, the similarity check finds no two sections
stating the same finding; tensions, motivations and objections all still
exist and each has a distinct job; objection cards show linked chips to
related items; what performs leads with takeaways; empty sections show a
reason and next steps.

V9. REVISED PACK PAGE AND HANDOFF                         (value rank 5)
--------------------------------------------------------------------------
Redesign the pack page around the condensed content (V4) and the new
sections (V5, V7, V8). Show me the V0 wireframe again with any changes
before building.

1. Structure: three clearly labelled parts, in this order:
   SUMMARY (first screen, readable in under a minute)
     - The brief as understood (audience, goal, market) in one line
     - What we found: 3 plain-language lines
     - Do this first: 1-3 actions
     - Five key truths, each with one quote and its strength badge
     - Ride this now: up to 2 news hooks (V7)
   UNDERSTAND YOUR AUDIENCE
     - Their words (vocabulary, phrases, do/don't say)
     - Pain points, Tensions, Motivations, Objections - as four short,
       distinct blocks with linked chips between related items (V4)
     - Segments (with empty-state reason if none)
     - Landscape: how the conversation differs by platform and over time
   ACT ON IT
     - Post briefs & content calendar (V8): brief cards with expandable
       drafts and copy buttons, a 4-week calendar grid
     - Channels (with timing chips) and what performs (takeaways first)
     - Opportunities (supported vs early signal, V5)
     - Guardrails
   THE RESEARCH (collapsed by default)
     - Sources kept and dropped, method, hypotheses table, blind spots,
       all evidence
2. Progressive disclosure: every card shows a headline, the so_what
   line and one quote; details, extra quotes and source links open on
   tap. No section shows more than its top items before "Show more".
3. Sticky navigation shows the three parts and their sections; a "How
   to read this" link explains strength badges in plain words, generated
   from scoring.yaml (e.g. "Strong - many different people in several
   communities say this"; "Early signal - only a few people, worth
   checking"), plus "seen in posts" vs "our interpretation" vs "from
   outside sources". Every badge has the same text as a tooltip.
4. Handoff panel, written for marketers - describe each option by what
   it is for and roughly how long it is, never in tokens or tech terms:
     - "Quick brief - half a page. Paste into ChatGPT or Claude to
       start writing."   (new short tier: audience, goal, top 3 truths,
       their words, 3 do / 3 don't)
     - "Brief for your AI writer - about 2 pages. Everything an AI
       copywriter needs: audience, language, rules, post ideas."
     - "Full report - for Notion, Google Docs or sharing with your team"
       (Markdown)
     - "Content calendar - import into Notion or a spreadsheet" (CSV)
     - "Send to Notion"
     - "Teach Claude this research - install once, Claude remembers it"
       (SKILL)
     - "For developers - data file and API" (JSON, link to API docs),
       visually de-emphasised
   Each option has a one-line preview of what's inside. Length labels
   are computed in code (words -> pages). After copying, a toast says
   what was copied ("Quick brief copied - paste it into your AI tool").
5. Rename "Replay research" to "Watch how this pack was made" with the
   note "a recording of the research - it won't run again or cost
   anything".
6. Mobile: one column, sticky part nav collapses to a menu, cards stack.
7. Markdown, Notion and PDF/print exports follow the same structure and
   order as the page.
CHECK: the first screen of a fixture pack shows the full Summary without

or evidence ids (grep the UI strings); every badge has a plain-language
